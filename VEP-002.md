# VEP-002: Capability Bit Registry (V1)

- Status: Draft
- Type: Standards Track
- Created: 2026-06-11
- Author: mjojo (https://github.com/GLK-Dev)
- Requires: VEP-001

## 1. Abstract
This proposal defines the canonical capability-bit registry for Velyx V1 negotiation.
It standardizes bit assignments, forward-compatibility rules, and implementation requirements for unknown capabilities.

## 2. Scope
This VEP defines:

1. V1 capability bit allocation.
2. Semantic categories for mandatory and optional features.
3. Rules for unknown bits and future extensions.

## 3. Capability Mask Type
1. Capability field type is unsigned 64-bit integer (u64).
2. Bit 0 is least significant bit.
3. Negotiated set is intersection: local_mask AND remote_mask.

## 4. V1 Registry
### 4.1 Core Capability Bits
1. Bit 0 (0x0000000000000001): CAP_FEC_V1
Meaning: Endpoint supports V1 fountain/FEC data-plane profile.

2. Bit 1 (0x0000000000000002): CAP_DHT_V1
Meaning: Endpoint supports V1 DHT discovery profile.

3. Bit 2 (0x0000000000000004): CAP_OBFS_V1
Meaning: Endpoint supports V1 obfuscation transport profile.

4. Bit 3 (0x0000000000000008): CAP_RELAY_V1
Meaning: Endpoint supports relay-assisted routing profile.

### 4.2 Reserved Ranges
1. Bits 4-15: Reserved for near-term standards-track VEPs.
2. Bits 16-31: Reserved for experimental/interoperability pilots.
3. Bits 32-47: Reserved for ecosystem/vendor extensions.
4. Bits 48-63: Reserved for future protocol generations.

## 5. Negotiation and Validation Rules
1. Endpoint MUST advertise only capabilities it can actually execute.
2. Endpoint MUST compute selected_caps as exact bitwise intersection.
3. Endpoint MUST NOT activate non-negotiated capabilities.
4. Endpoint MUST fail handshake if peer echoes selected_caps outside intersection.

## 6. Unknown Capability Handling
1. Unknown bits advertised by peer MUST be ignored for activation.
2. Unknown bits MUST still be retained for logging/diagnostics.
3. Unknown bits MUST NOT cause handshake failure by themselves.

## 7. Security Considerations
1. Capability over-claiming can create downgrade or state-confusion risk.
2. Implementations SHOULD couple capability activation to explicit code paths and tests.
3. Selected capability set SHOULD be logged with session metadata.

## 8. Interoperability Notes
1. V1 interop baseline SHOULD include CAP_FEC_V1 and CAP_OBFS_V1 where available.
2. Implementations with minimal transport MAY negotiate empty selected_caps if protocol version matches and both sides accept baseline operation.

## 9. Initial Test Guidance
Implementations SHOULD verify:

1. intersection correctness under mixed masks.
2. rejection of invalid echoed selected_caps.
3. stable encoding/decoding of negotiation payloads.

## 10. Reference
1. VEP-001 defines packet and negotiation message wire layout.
2. Reference implementation constants currently live in src/lib.rs.
